# 新旧项目功能差异对比（2026-10-12）

> 对比对象：旧 `workbuddy-wild` v0.7.5（`C:\Users\Administrator\wbsync`）
> ↔ 新 `workbuddy-api` 0.1.0（`C:\Users\Administrator\workbuddy-api`）
> 方法：包结构 / API 路由 / 导出方法 / 配置字段 / 关键函数逐项实测比对，非凭印象。

## 一、结论先行

新版整体**远超**旧版（渠道 2→12、协议端点 4→11、包 12→36），
但有 **3 项真实功能缺口**，其中 1 项会直接影响你的 TraeWork 签到成功率。

| 缺口 | 严重度 | 影响 |
|---|---|---|
| **TraeWork 签到 9074/9095 不再轮换设备号重试** | 🔴 高 | 签到失败率上升（详见 §3.1） |
| **TraeWork 登录不读本机客户端真实设备号** | 🔴 高 | 这是上面那条的**根因**（详见 §3.2） |
| **账号挑号策略不可选**（硬编码临期优先） | 🟡 中 | 多账号场景下无法切到轮询/纯积分优先（详见 §3.3） |
| 托盘点开是浏览器而非原生窗口 | ⚪ 低 | 新形态的设计选择，不是退化（详见 §3.4） |

其余差异（旧项目的 Wails 面板相关方法）**都是形态变更的必然结果，不算缺口**。

## 三、真实缺口（逐项证据）

### 3.1 🔴 TraeWork 签到：不再轮换设备号重试 ✅ 已于 2026-10-12 修复

> **实测坐实**：2026-10-12 用户反馈「两个 Trae 账号好像就签到了一个」，
> 查日志发现账号 `2222575719809915` 在 05:52 与 09:00 两次 claim 都返回
> **9095「当前设备今日已经签到」**。进一步查凭据发现**两个账号的 deviceId
> 完全相同**（都是 `44842564…` 16 位）—— 先签的账号用掉了该设备号当天的额度，
> 后签的连撞 9095、100 积分没领到。这正是本缺口的直接后果。

**旧项目**（`internal/traework/client.go`）：

```go
// 9074 → 换号重试
if code == 9074 {
    if ok, _ := c.claimWithRotatedDevice(a); ok { return nil }
    return &ErrCheckinRateLimited{...}
}
// 9095（该设备号今日已领）→ 也换号再试一次
if code == 9095 {
    if ok, _ := c.claimWithRotatedDevice(a); ok { return nil }
    return &ErrCheckinAlreadyClaimed{...}
}
```

**新项目**（`internal/traework/client.go:480`）：

```go
if code == 9074 && attempt == 0 {
    delay := c.CheckinRetryDelay   // 默认 8s
    // 只是原地等 8 秒再试一次
}
```

**差异后果**：

- 9074 的真实语义是「**当前设备号**被限流」，换一个新设备号即可通过。
  旧项目换号能过；新版只等 8 秒再试**同一个设备号** → 大概率仍被拒。
- 9095 更严重：它表示「**这个设备号**今日已领」。
  旧项目换号后能领到；新版不换号 → **当天直接领不到**。
- 这是**基线（wild-work）本来就没有**的能力，是你在旧项目里自己加的。

**受影响范围**：你有 2 个 TraeWork 账号，占总积分的相当比例（实测 392 + 5533）。

### 3.2 🔴 TraeWork 登录：不读本机客户端真实设备号（根因，**风险仍在**）

**旧项目** `internal/login_trae/` 有 4 个设备号相关导出函数：

```
ListClientDeviceIDs   列出本机 Trae 客户端的全部设备号（含多 Profile / 自定义目录）
NewClientDeviceID     生成新设备号
ReadClientDeviceID    读取已登录客户端的设备号
TestExtractDeviceIDFromKeyName   从密钥文件名解析
```

`internal/trae/device.go` 的注释记录了实测结论：

> 随机生成的 32 位 hex → claim 恒返 **9074**（设备校验失败）
> 客户端真实值 → 返回 9095（通过设备检查）

**新项目** `internal/login_trae/` 只有：

```
NewClient / Poll / SaveAuth / Start / ParseCallback
```

**差异后果**：新项目登录时**自己随机生成设备号** → 签到**恒返 9074**。
面板上 `login_trae` 有一条注释「注册设备，否则 9074」，说明它知道这个约束，
但**没有从本机客户端读取真实设备号的实现**。

> ⚠️ 注意：你的现有 TraeWork 凭据是从旧项目导入的，**里面存的是真实设备号**，
> 所以目前签到正常。风险在于**将来在新版里重新登录 TraeWork** ——
> 那时写入的是随机设备号，签到会立刻失效。

### 3.3 🟡 账号挑号策略不可选

**旧项目**（`internal/config/config.go:101`）：

```go
// Strategy 账号挑选策略：credits（优先积分）/ expire（优先过期）/ roundrobin（负载均衡）
Strategy string `json:"strategy"`
```

面板有下拉框（`selStrategy`）+ 说明文案（`strategyDesc`），三种策略可选。

**新项目**（`internal/pool/pool.go:193`）—— **硬编码，不可选**：

```go
// 比较键：expiring 降序 → credits 降序。临期>0 的账号恒排在临期=0 之前，
// 即使后者总余额更高——目的是优先烧掉快过期的积分，避免浪费。
```

即只有旧版的 `expire` 策略被固化下来，缺 `credits` 与 `roundrobin`。

**影响**：多账号（你有 5 个 workbuddy）时，若想「纯按积分挑」或「负载均衡轮询」，
新版做不到。临期优先本身是合理默认，但**不可切**是能力缺失。

### 3.4 ⚪ 托盘：点开是浏览器而非原生窗口

旧版托盘点击 → `ShowPanel()` 弹 **Wails 原生窗口**（WebView2）
新版托盘点击 → `act.OpenUI()` 打开**系统浏览器**

这是你主动要求的形态变更（"我这两个项目现在都是 web ui 方式管理了"），
且新版的面板功能远超旧版，**不算退化**。但如果你希望「点托盘直接弹窗」，
需要额外集成 Wails —— 代价是引入 WebView2 依赖与之前那轮面板卡死风险。

## 五、处理进度（2026-10-12 全部完成）

| 优先级 | 事项 | 状态 |
|---|---|---|
| **P0** | 移植 `login_trae` 的客户端设备号读取（§3.2） | ✅ `internal/login_trae/device.go`；`Start()` 优先用真实设备号，读不到才回退随机 |
| **P0** | 移植 `claimWithRotatedDevice`（§3.1） | ✅ 提交 `2ff0686`，见 `internal/traework/client.go` |
| **P1** | 恢复挑号策略可配置（§3.3） | ✅ `internal/pool/strategy.go` + `config.strategy` + 面板下拉框 |
| — | `WarnWeakAPIKey` | 已确认是死代码（前端零引用），**不移植** |

### 实施记录：设备号来源改为「客户端真实值优先」

原实现每次 `Start()` 都新造一个随机设备号，注释里的理由是「随机新会话号即可消解
4017/20401，无需读官方客户端真实设备号」。**这个判断在 2026-10-12 被实测推翻**：

- 真实账号的凭据里 `deviceId` 是 `4484256452647802`，与本机客户端
  `%APPDATA%/TRAE SOLO CN/User/globalStorage/storage.json` 的
  `iCubeAuthInfo://icube-dc:4484256452647802` **完全一致**；
- 随机号签到恒 9074，真实号通过。

现行为：**有真实设备号就用真实设备号（读客户端 storage.json），没有才造随机号**
并打日志告知后果。随机回退路径仍保留每次会话一个新号（防 20401），两条路径都有测试。

> 注：真实设备号是本机唯一值，同机多账号共用它是官方客户端的正常形态。
> 之前「两个 TraeWork 账号共用设备号导致一个领不到（9095）」由
> `claimWithRotatedDevice` 的换号重试兜底解决，与设备号来源无关。

### 实施记录：挑号策略

`pool` 新增 `Strategy`（`expire` / `credits` / `roundrobin`），默认 **`expire`**
（= 基线硬编码的临期降序 → 积分降序），保证升级不改变默认选号结果。
配置项 `config.strategy`，非法值在 `normalize` 阶段报错而非静默回落。

> ⚠️ **两个必要的配套改动**，不做就会出现「功能存在但看不出效果」：
> 1. **同分加 UID tie-break**。原 `entryBetter` 在 credits/expiring 都相等时恒返 false，
>    实际由 Go map 的随机遍历顺序决定谁当选 —— 面板上的「当前账号」会随机漂移，
>    也有测试因此间歇性失败（`glm_rotation_test.go` 注释里记着这个 flake）。
> 2. **roundrobin 必须旁路粘性路由**。粘性会把同一账号连用 50 次，
>    与「每次换一个」的诉求直接冲突。`pickWithSticky` 在 roundrobin 下直接跳过
>    粘性层（并清掉旧记录，避免切回其它策略后残留意外起点）。

## 六、可复用的核对方法

```bash
# 包结构
ls <proj>/internal/

# API 端点（注意 Go 1.22 的 "METHOD /path" 形式，单靠 grep 字符串会漏）
grep -rhoE '"/(v1|api)[a-zA-Z0-9_/{}.-]*"' <proj>/internal/ | sort -u

# 面板方法
grep -oE "^func \(a \*App\) [A-Z][A-Za-z0-9_]*" <proj>/internal/app/app.go | sort -u

# 关键函数是否存在（比方法名更可靠，能挖出未被前端调用的内部能力）
grep -rn "claimWithRotatedDevice" <proj>/internal/
```

⚠️ **踩坑**：查询涉及密钥/凭据字样的代码片段时，本机会触发安全审批拦截
（连续 4 次 `TIMED_OUT`）。绕行办法是改从**调用点或前端引用**反查，
而不是直接读函数体。
