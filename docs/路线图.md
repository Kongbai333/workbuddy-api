## 一、本项目是什么

`workbuddy-api` 是一个**独立的新项目**，目标形态是**纯 Go + Web UI 管理**（无 Wails / WebView2 依赖）。

它与既有项目的关系：

| 项目 | 关系 | 状态 |
|---|---|---|
| **本仓库 `workbuddy-api`** | 新项目，以 wild-work v2.6.2 为基线 | 🚧 建设中 |
| `rockswang/wild-work` | **基线来源**（v2.6.2） | 上游，持续参考 |
| `linguo2625469/workbuddy2api-panel` | **能力来源**（任务体系等） | 第三方，参考 |
| 旧项目 `workbuddy-wild` / `wbsync` | **保留不动**，Wails 桌面形态 | ✅ 原样保留，不受影响 |

> ⚠️ 旧项目**不做任何修改**。本项目在独立目录、独立 git 仓库中演进，
> 两者数据目录相互独立（首次启动可从旧目录导入账号凭据，见下）。

## 二、为什么选 wild-work 作基线

两个参考项目**互补而非包含**（实测）：

| 能力 | wild-work v2.6.2 | panel v1.13.0 |
|---|---|---|
| **任务体系**（成长任务 / 连登 / 旅行 / 活跃） | 0 | **19 个文件** |
| **TraeWork 渠道** | **14 个文件** | 0 |
| 其他渠道（qoder / qwenwork / raccoon / loomy / monkeycode / oczen / glm） | **97 个文件** | 0 |
| 多渠道路由（provider + gateway） | **16 个文件** | 0 |
| Web 面板 | ✓ | ✓ |
| Docker | 0 | **4 文件** |

两者共有的 `internal` 包**只有 5 个**（auth / pool / scheduler / server / upstream）。

**选 wild-work 的理由**：TraeWork 与多渠道路由只在它这里有，且它已是纯 Go Web UI 形态、
与本项目目标一致、与旧项目同源（旧项目即从它 v0.2.2 切出）。

### ✅ P1 · 身份与配置对齐（2026-10-11，commit `3ba3d52`）

**单实例锁**（基线缺失）：
- `internal/platform.AcquireSingleInstance(name)`
  - Windows：`CreateMutexW`（`Local\` 命名空间）—— 句柄由系统在进程退出时自动释放，
    不存在崩溃后遗留陈旧锁的问题
  - darwin / other：无操作（重复启动会因端口被占立即失败，危害有限），避免破坏跨平台构建
- 接入位置**必须在浣熊回调之后**：回调是「非守护」调用（`--raccoon-callback`），
  需在守护进程运行时也能执行；若在它之前抢锁会导致授权码落不了盘、登录链路断掉

**首次启动导入**（`cmd/workbuddy-api/firstrun_import.go`）：
- 触发条件严格三项同时满足：真首次启动 + 目标 `auths/` 为空 + 找到源目录
- 只复制 `auths/*.json`；**不复制 `data/`**（冷却与签到状态属运行时产物，
  带过来会引入过期冷却），也不自动复制 `config.json`
- 跳过 `*.bak*`；目标已存在的同名文件不覆盖
- 支持 `--import-from <dir>` 显式指定源目录；全程写日志

### ✅ P2b-1/2 · 上报原语泛化 + 成长自动化（2026-10-11，commit `a4b294c`）

**一、上报原语泛化**（事件伪造的前置）

基线 `report.go` 只能发**一种硬编码事件**（`chat_request_send` + 固定模型），
而编排层需要任意事件载荷。新增：

- `ReportEvents(a, []map[string]any)` — 任意事件数组
- `ReportEventsRaw(a, json.RawMessage)` — 直通已序列化载荷
- `ChatRequestSendEvent(...)` — 事件构造函数
- `ReportChatActivity` 改为薄包装（签名不变）

删除了 `chatRequestEvent` 结构体，改由 map 承载 —— 避免同一事件形状
两处定义而漂移。

**二、成长自动化**（连登兑换+抽奖 / 猫猫旅行）

选择这两项而非「17 个任务」作为第一步，理由是它们**不是事件伪造**：

| 动作 | 为什么可以自动跑 |
|---|---|
| 连登兑换 | 按档位状态调用，未解锁由服务端 403 拒绝，天然幂等 |
| 抽奖 | 次数只能从兑换获得，用掉即减少 → 加了单次上限保护（30 次） |
| 猫猫旅行 | 每自然日仅可派一次（上游 `daily_limit_reached` 控制） |

而任务体系靠**伪造客户端行为事件**，载荷依赖上游实现细节，变更风险高。

关键实现取舍：
- 调度器用**可选接口探测**（`growthAutomator`）而非 import 具体渠道包，
  接口只返回基本类型 —— 保持调度器与渠道解耦
- 错误分类 `IsGrowthUnsupported` / `IsGrowthTransient`：避免把
  「渠道不支持」误记为账号故障而冷却健康账号
- **仅在命中配置签到时刻时触发**（不在窗口重试的每分钟重复跑），
  当日只跑一次（`growthDoneDay` 标记 + `retryMu` 保护），异步执行不阻塞定时器
- 仅接入 workbuddy 渠道（成长接口仅国内版提供）

**配置开关（默认全部关闭）**

```json
"schedule": {
  "growth_redeem_streak": false,   // 连登兑换 + 抽奖
  "growth_travel": false,          // 猫猫旅行
  "growth_travel_location": 1      // 1~4，0 或越界取 1
}
```

> ⚠️ 这两项会**真实改变账号状态**（抽奖次数用掉不可撤销），
> 故默认关闭，必须由用户显式开启。

### ✅ P2c · 成长任务「一键完成」编排（2026-10-12）

**范围**：把任务码 → 一组客户端行为的映射跑起来，并在进度达标时自动领奖。
共 **24 个动作**（对应 18 个常规任务 + 8 个小程序任务，多个任务共用同一动作）。

**默认关闭，只能手动触发**（`config.schedule.growth_tasks` 控制的是「是否随每日首个签到时刻自动跑」）。

**新增文件**

| 文件 | 作用 |
|---|---|
| `internal/upstream/desktop.go` | 桌面 / Web 指纹上报 + 事件链构造（RichMeow、Buddy App、模板、灵感、画布、专家、皮肤、技能） + 专家市场 |
| `internal/upstream/mp_report.go` | 小程序指纹上报 + mp 事件构造（校园日、mp 对话、mp 专家、mp 灵感） |
| `internal/upstream/growth_tasks.go` | 动作表 + 执行器 + 回读领奖 + 调度器入口 |
| `internal/app/tasks.go` | 面板侧异步执行、进度查询、开关热更新 |

**四条关键设计**

1. **判定一律以「回读进度」为准，不看 HTTP 状态码。**
   字段名写错时上游仍返回 200（只是不入账）。所有动作执行后都回读任务列表，
   若进度到了就领奖，没到则在结果里写明「进度 x/y（未达 N）」。
2. **异步执行 + 轮询进度。** 单账号几十个请求、多账号可到数分钟，
   同步 HTTP 会撞上前端/反代超时。故 `POST /api/account/tasks` 立即返回，
   `GET /api/account/tasks_status` 轮询。
3. **DryRun 零写请求。** `GrowthTaskOptions.DryRun` 只读列表并汇报「打算做什么」，
   有专门的护栏测试断言此时 POST 数为 0。
4. **领奖后必须刷新余额（2026-10-12 补）。** 面板 `/api/state` 的 `credits`
   读自 **pool 缓存**（`SetCreditDetail` 写入），任务执行本身不会改它 ——
   只 `loadState()` 会看到领奖前的旧值，表现为「任务做完了但积分没变」，
   用户会误判成没领到奖。故：
   - 后端 `runTasks` 末尾对**有到账的账号**调 `RefreshCredits`
     （覆盖无头/定时触发、页面关闭等场景）
   - 前端收尾再刷一次 `refresh_all` 兜底，并按
     「刷新后余额 − 执行前余额」算出**真实增量**，在卡片与结果面板高亮 `+N`
   - 未领到奖励时**不刷新**（避免给上游平白增加请求），有对应护栏测试

**执行范围**：只对**成长中心支持的渠道**（当前仅 WorkBuddy 国内版）收集目标。
其余渠道会在任务解析阶段被跳过 —— 否则每个账号都要白跑一次 404 往返。

**面板入口**

- 账号列表工具栏「一键做任务」（全部账号）
- 每张账号卡片上的 ★（单账号）—— 仅成长中心支持的渠道显示（后端按渠道下发 `growth` 标志）
- 设置弹层「成长中心自动化」四项开关（兑换/旅行/任务/任务含小程序），保存后**热生效**

**⚠️ 未实测的部分（重要）**

事件形状来自第三方项目 `linguo2625469/workbuddy2api-panel` 的抓包与 asar 逆向，
**本项目未独立验证**。首次使用请：

1. 先只对**一个**账号点击执行（不要用「一键做任务」全量跑）
2. 核对结果面板里哪些任务真的 `done`/`claimed`，哪些停在「进度未达」
3. 确认无误后再考虑开启自动

已知不可自动化：`Expert_Philanthropy` 需真实捐款回执（服务端校验），**17/18 是上限**。

**小程序任务默认不跑**：Sequential_Tasks_3 一类有反作弊 —— 数秒级连发会先计入进度、
随后被整体回滚；第三方实测 45s 间隔才存活。故 `include_mp` 默认 false，
且自动执行时另有 `growth_tasks_include_mp` 开关（默认 false）。

### ✅ P3 · Docker / fnOS 部署 + 容器前置修复（2026-10-11，commit `P3-1` / `P3-2`）

**一、两处必须先修的问题**（不修则容器部署跑起来也是错的）

| 问题 | 后果 | 修法 |
|---|---|---|
| 精简镜像无 `/usr/share/zoneinfo`，Go 无法解析 `TZ` | `time.Local` **静默退化 UTC** → 签到在北京时间 17:00/05:00 触发，日志无异常 | `main.go` 内嵌 `import _ "time/tzdata"`（+397 KB，实测 `PST8PDT` 从 0 → 11 处） |
| `config.json` 不存在时 `applyEnv` 被跳过 | 「纯 env 部署」静默失效 → 容器用上默认 `127.0.0.1` + 默认密钥，表现为「起来了但端口不通」 | 新增 `config.LoadOrCreate`：`Default() + applyEnv + normalize` 再落盘 |

**二、Docker 资产**（`docker/`，8 个文件）

| 文件 | 作用 |
|---|---|
| `Dockerfile` | alpine 基础镜像，**零 apk 依赖**（时区已内嵌、登录走面板无需 CLI 助手） |
| `entrypoint.sh` | `WILDWORK_*` → 容器内 `config.json`；对外监听无密码时**拒绝启动**；`exec --no-tray` |
| `docker-compose.yml` | NAS 现场构建版（`docker compose up -d --build`） |
| `fnos-compose.yml` | fnOS 图形界面粘贴版（含 ★必改 标注） |
| `build-binary.sh` | 开发机交叉编译（含 ELF 与时区库自检） |
| `build-image.sh` | 有 Docker 的机器：构建 + 导出离线 tar + `SHA256SUMS` |
| `build-on-nas.sh` | NAS 现场构建（含 ELF 与 CRLF 检查） |
| `load-image.sh` | NAS 导入离线镜像（校验 SHA256 + `docker load`） |

沿用旧项目经过验证的设计：**只 COPY 预编译静态二进制**（规避 NAS 上 GOPROXY 超时）、
**配置在容器内生成、绝不 bind 挂载单文件**（规避「单文件被挂载成空目录」导致 `Exited:0`）。

**三、与旧项目 `workbuddy-wild` 的差异**

| 项 | 旧 | 本 |
|---|---|---|
| 环境变量前缀 | `WB2A_*` | **`WILDWORK_*`** |
| 二进制数 | 3（server + 2 个登录助手） | **1**（登录走 Web 面板） |
| 面板路径 / 鉴权 | `/admin/` + `WB2A_ADMIN` 开关 | **`/`** + `WILDWORK_ADMIN_PASSWORD`（对外监听必填） |

**四、验证**

### 🔧 修复 · 导入旧项目凭据后面板积分全为 0（2026-10-11）

**现象**：用 `--import-from` 从旧项目导入 `auths/` 后，面板 8 个账号积分全部显示 0。
日志里错误分成**两类形状** —— 这个差异是定位关键：

| 渠道 | 错误 | 含义 |
|---|---|---|
| workbuddy ×5 | `401` + **openresty HTML 页面** | 请求在**网关层**就被拒，没到业务层 |
| traework ×2 | `refresh token is invalid` 业务 JSON | 请求到达了上游，token 本身无效 |

**根因**：旧项目在 Windows 上用 **DPAPI 加密** token（`dpapi:` 前缀，密文与当前用户绑定），
而本项目当时**没有任何加解密代码** → `Authorization: Bearer dpapi:AQAAANCM...` 被原样发出。

**修复**：
- 移植 `internal/auth/secure_windows.go`（DPAPI）+ `secure_other.go`（非 Windows 明文直通，
  对 `dpapi:` 返回空串并告警）
- **读**：`Parse` / `parseAllowMissingAccessToken` 在空值校验**之前**解密
- **写**：11 处全覆盖（`saveAtomicLocked` + `writeAuthFile` + 8 个登录包）

**验证**：新增 8 例测试；反向验证（移除解密 → 3 例 FAIL 并打印出密文）；
真实账号实测 7 个账号积分正常（合计 **19792**）。

**⚠️ 平台绑定（部署须知）**：Windows 的 auths 是 DPAPI 密文，**不能拷进 Linux 容器**
（密文无法跨平台解密），需在容器内重新登录；反向（Linux → Windows）可以。

**★ SingleAccount 机制保留（关键取舍）**

`server.Runtime.SingleAccount` 是**结构化通用能力**（不硬编码渠道名），不随渠道一起删。
两个依赖它的测试改用**自造渠道标识**（`singleacct` + 自建 Auth）继续覆盖，语义不变。

顺带**增强**了这组测试：假上游的 `Classify` 现在故意返回「通常会引发惩罚」的分类
（429 → `ErrSoftRate`、5xx → `ErrServer`）。若 `SingleAccount` 的短路失效，账号会被冷却、
测试立刻失败 —— 原先若用渠道自带的分类（本身就不罚号），断言会变成**假阳性**。

## 七、构建

```bash
# Windows（开发构建，带控制台便于看日志）
go build -o dist/workbuddy-api.exe ./cmd/workbuddy-api

# Windows（发布构建，隐藏控制台）
go build -ldflags "-H windowsgui" -o dist/workbuddy-api.exe ./cmd/workbuddy-api

# 跨平台（macOS 需在 macOS 上构建，第三方 systray 需要 cgo）
GOOS=linux GOARCH=amd64 go build -o dist/workbuddy-api-linux-amd64 ./cmd/workbuddy-api
```

**已知约束**：macOS 目标无法从 Windows 交叉编译 —— 第三方 `energye/systray`
的 darwin 实现需要 cgo，必须在 macOS 上构建（基线 CI 亦如此）。

**容器（见 [docker/README.md](../docker/README.md)）**：

```bash
sh docker/build-binary.sh     # 开发机：交叉编译 linux/amd64（含 ELF 与时区库自检）
sh docker/build-image.sh      # 有 Docker 的机器：构建镜像 + 导出离线 tar + SHA256SUMS
sh docker/build-on-nas.sh     # NAS 上：现场构建镜像
```
